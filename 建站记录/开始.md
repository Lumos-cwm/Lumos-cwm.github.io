## 博客原理

- 首先博客有一个总的项目文件夹用于存放文章，站点配置，主题模板等博客源文件。
- Hexo 读取博客源文件，生成 HTML、CSS、JavaScript 等静态网站文件。
- Git 对博客源文件进行版本管理，用于记录和比较修改，也可以在需要时回退到以前的版本。
- GitHub 在云端托管博客源文件。
- GitHub Actions 是自动化工具。将本地博客源文件上传至 GitHub 后，由 GitHub Actions 生成静态网站文件，并交给 GitHub Pages 发布网页。
- GitHub Pages 用于发布并托管构建后的静态网站，使用户能够通过网址访问博客。

## 安装前置软件

### 安装 Git

[link](https://git-scm.com/install/windows)

### 安装 Node.js

[link](https://nodejs.org/zh-cn/download/)

Node.js 为 JavaScript 文件运行提供环境。

安装 Node.js 时通常会同时安装 npm（Node Package Manager）。npm 用于下载和管理 JavaScript 工具及其依赖。

npx 是 npm 5.2.0 版本引入的命令行工具，它让你可以执行 npm 包而无需全局安装。

想象一下你家的工具箱：

- **npm** 就像是你的 **工具仓库管理员**。当你 `npm install -g some-tool` 时，相当于告诉管理员：把这个工具买回来，永远放在我们家车库（全局环境）里。
- **npx** 则像一个 **即时跑腿服务**。当你 `npx some-tool` 时，相当于告诉跑腿小哥：去帮我找个 `some-tool` 来用一下，用完就还回去，别放我家。

PS：可以去看 [菜鸟教程](https://www.runoob.com/nodejs/npx-intro.html)，这里面解释很详细。

### 安装 hexo-cli 

在 Git Bash 中执行：

```bash
npm install -g hexo-cli
```

hexo-cli 将 Hexo 的功能封装为命令，提供给用户通过 hexo server / hexo deploy 等命令调用。 CLI = Command Line Interface，即命令行界面。

`-g` 表示全局安装， 在系统的全局环境中都可以识别 hexo 命令。

## 创建 GitHub 仓库

新建仓库，仓库名称写 `用户名.github.io`，用户名指的是 GitHub 用户名。

创建仓库时不要勾选 `Add a README file`，不要添加 `.gitignore` 和 `License`，保持仓库为空。否则远程仓库会创建一个本地没有的提交，之后把本地文件上传到 GitHub 远程仓库时会因为远程仓库包含额外历史而被拒绝。

## 创建 Hexo 博客

创建一个文件夹 `Blog` 用来存放博客项目。

在 `Blog` 目录下执行：

```bash
hexo init myblog
```

`Blog/myblog` 作为当前博客项目的根目录。

上面这个指令会初始化 `myblog` 根目录，加入一些 Hexo 的初始文件，主要结构如下：

```
myblog
├── _config.yml Hexo 的主要配置文件
├── package.json 记录博客需要安装哪些工具和插件
├── scaffolds 新建文章时使用的模板
├── source 存放文章和页面
	├── _posts 存放博客文章
├── themes 存放主题
└── node_modules npm 下载的软件包
```

在 `myblog` 目录下执行：

```bash
npm install
```

npm 会读取当前项目的 `package.json` 并安装所需软件包，存储到 `node_modules` 里。

## 如何在本地预览博客

现在我们安装好了一个 Hexo 的默认博客，要在本地预览它。

回到博客根目录，即 `myblog`。可以执行以下命令：

```bash
hexo clean
```

删除以前生成的缓存和网页文件。

```bash
hexo generate
```

把当前博客项目转换成网页文件存储在 `myblog/public` 中，可以用于检查网页文件。

```bash
hexo server
```

启动本地临时服务器，根据博客源文件来生成网页，注意这一步并不需要提前生成 `public`。

Git Bash 中一般会提示 `Hexo is running at http://localhost:4000/`，在这个网址访问即可。

打开 `_config.yml`，找到：

```yaml
author: Lumos
```

```yaml
url: https://用户名.github.io
```

## 新建第一篇文章

在根目录执行：

```bash
hexo new "post-name"
```

Hexo 会创建 `myblog/source/_posts/post-name.md`，

打开文章后，头部的是文章的信息区，又称 Front Matter，供 Hexo 读取文章时用。

```markdown
---
title: post-name
date: 发布时间
tags: ["...", "...", ...]
categories: ["...", "...", ...]
---
```

这样 Hexo 生成网页时会自动给文章加 Tag 或者分类。

注意 `tags` 可以包含多个并列标签；`categories` 中的多个项目默认表示从前到后的层级分类。

在 `_config.yml` 中找到配置：

```yaml
post_asset_folder: true
```

这样会在新建文章时在 `_posts` 中生成同名文件夹，可以用于存放文章的图片等资源。

## 安装主题（Butterfly）

### 安装

在博客根目录执行：

```bash
npm install hexo-theme-butterfly --save
```

安装主题需要的渲染器：

```bash
npm install hexo-renderer-pug hexo-renderer-stylus --save
```

### 启用

打开博客根目录的：

```text
_config.yml
```

配置：

```yaml
theme: butterfly
```

### 配置

Butterfly 会在 `node_modules/hexo-theme-butterfly/_config.yml` 中存储主题的默认配置。

如果要修改主题配置，把这个文件复制到 `myblog/_config.butterfly.yml`，然后修改 `_config.butterfly.yml` 即可，不要修改 `node_modules` 中的文件。

## 配置 Git 的用户名和邮箱

第一次使用 Git 时，需要设置提交者身份。

设置用户名：

```bash
git config --global user.name "你的 GitHub 用户名"
```

设置邮箱：

```bash
git config --global user.email "你的 GitHub 邮箱"
```

检查配置：

```bash
git config --global --list
```

`--global` 表示对当前电脑用户下的所有 Git 仓库生效。


这个文件表示上传项目到 GitHub 仓库时忽略（不上传）哪些文件。

## 把本地项目连接到 GitHub

### 初始化

在根目录执行：

```bash
git init
```

会在当前文件夹创建一个隐藏目录：

```text
.git
```

这个目录专门保存：

- 文件修改记录
- 提交历史
- 分支信息
- 远程仓库地址

终端出现 `(main)`，是因为 Git Bash 检测到了这个 `.git` 目录。

### 命名主线

执行：

```bash
git branch -M main
```

把当前博客的版本历史主线命名为 `main`。

### 连接 GitHub 仓库

执行：

```bash
git remote add origin https://github.com/用户名/用户名.github.io.git
```

相当于告诉本地 Git 项目需要连接的远程仓库的地址。

`origin` 是 Git 给远程仓库起的简称，原本很长的地址 `https://github.com/用户名/用户名.github.io.git` 以后可以用 `origin` 代替。

检查：

```bash
git remote -v
```

应该看到类似：

```text
origin  https://github.com/用户名/用户名.github.io.git (fetch)
origin  https://github.com/用户名/用户名.github.io.git (push)
```

修改远程仓库地址可以用：

```bash
git remote set-url origin [new-link]
```

## 配置 GitHub Actions 自动部署

我们要让 GitHub 上的机器人自动构建博客：

- 安装 Node.js
- 安装 Hexo 依赖
- 生成 public
- 发布到 GitHub Pages

### 创建工作流目录

创建 `myblog/.github/workflows`。

GitHub 会自动识别这个目录中的 YAML 文件，并把它们当作自动化任务。

### 创建部署文件

创建 `.github/workflows/deploy.yml`，写入：

```yaml
name: Deploy Hexo to GitHub Pages

on:
  push:
    branches:
      - main
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: 获取博客源文件
        uses: actions/checkout@v4

      - name: 安装 Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: 安装项目依赖
        run: npm ci

      - name: 配置 GitHub Pages
        uses: actions/configure-pages@v5

      - name: 使用 Hexo 生成网页
        run: |
          npx hexo clean
          npx hexo generate

      - name: 上传生成的网页
        uses: actions/upload-pages-artifact@v3
        with:
          path: ./public

  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}

    runs-on: ubuntu-latest
    needs: build

    steps:
      - name: 发布到 GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

#### 详解

```yaml
name: Deploy Hexo to GitHub Pages
```

是自动部署任务的名称，会显示在 GitHub 的 `Actions` 页面。

```yaml
on:
  push:
    branches:
      - main
  workflow_dispatch:
```

表示推送到 `main` 分支时自动执行。`workflow_dispatch:` 表示也可以手动执行。

```yaml
permissions:
  contents: read
  pages: write
  id-token: write
```

给自动机器人权限：

- `contents: read`：允许读取博客源文件
- `pages: write`：允许发布到 GitHub Pages
- `id-token: write`：允许验证部署任务的身份

`concurrency` 用来限制同一组工作流任务的并发执行。

```yaml
group: pages
```

表示把使用同一个并发组名称 `pages` 的工作流运行归为一组。

同一时间，这一组通常只允许一个工作流运行，另一个新触发的运行会进入等待状态。这样可以避免两次 Pages 部署同时操作，造成部署顺序混乱。

```yaml
cancel-in-progress: false
```

表示当新任务触发时，不要取消当前正在运行的旧任务。

```yaml
runs-on: ubuntu-latest
```

表示 GitHub 会临时提供一台 Ubuntu 云端电脑。

```yaml
needs: build
```

用来建立任务依赖，会先 `build` 再 `deploy`。

```yaml
environment:
  name: github-pages
  url: ${{ steps.deployment.outputs.page_url }}
```

`environment: name:` 用来设置这个 `job` 部署的环境。你可以创建环境，并使用部署保护规则保护这些环境。引用某个环境的 `job` 必须遵循该环境的所有保护规则，然后才能运行或访问该环境的机密。

`environment: url:` 是本次部署结果的访问链接。

## 开启 GitHub Pages

打开你的 GitHub 博客仓库，然后进入 `Settings → Pages`，找到 `Build and deployment`，把 `Source` 设置为 `GitHub Actions`。

## 向 GitHub 提交博客源文件

在根目录执行：

```bash
git add .
```

把当前目录全部修改放入 "待提交区"。

```bash
git commit -m "本次修改说明"
```

记录 "待提交区" 的修改，并附上说明。

```bash
git push -u origin main
```

把本地 `main` 分支的提交上传到 GitHub 的 `origin` 仓库。

- `origin`：GitHub 仓库的简称
- `main`：当前主分支
- `-u`：建立本地 `main` 和远程 `main` 的对应关系

第一次需要使用 `git push -u origin main`，因为 `-u` 已经修改了默认对应关系，后面用 `git push` 即可。

## 查看部署情况

GitHub Actions 检测到 `main` 分支有 `push`，会自动进行部署。

在仓库主页找到 `Actions`，进入页面可以查看部署情况。
